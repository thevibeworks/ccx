* [2026-05-24] Insight HTML Report                            :ARCH:FEAT:

** Tension

The previous pivot fixed the core product boundary: =ccx log= should provide
time-sliced evidence, and =/ccx-insight= should interpret it. But the skill
still had a weak human artifact contract.

It said "write a standalone HTML report" and listed sections. That was not
enough. A future agent could still produce a pretty narrative that repeated
the original mistake: making source log files look like clean sessions,
treating assistant prose as proof, and hiding provider-specific caveats under
polished status labels.

The release risk was concrete. We had already seen a false claim from the old
shape: =amux= was reported as "review done but not published yet" even though
raw evidence showed repo creation, push, tag, and CI activity. If the HTML
report is vague, it will make wrong summaries feel more trustworthy.

The useful primitive now exists: =ccx log= emits a =ccx.log.v1= evidence
bundle with =scope=, =metrics=, =sessions[]=, and =records[]=. The schema
exposes the details the report must respect:

- =metrics.sessions= is a count of source log files, not necessarily clean
  logical sessions.
- =sessions[].relation= marks long-running containers.
- =records[].kind= separates =user_prompt=, =assistant_message=,
  =tool_call=, =tool_result=, =reasoning=, =summary=, and =compaction=.
- =records[].is_subagent= and source paths under =/subagents/= expose Claude
  Code sidechain evidence.
- =source_file= and =line= give reportable provenance.

The examples were not abstract:

- Codex sessions can emit duplicate-looking user and assistant records from
  both =event_msg= and =response_item=. Counts are useful, but meaning must be
  deduplicated semantically.
- Claude Code sessions can carry sidechain/subagent JSONL files under the
  parent session. Those are evidence lanes, not separate human workstreams by
  default.
- Compaction and continuation summaries are useful context, but they are
  lossy. They cannot prove completion.
- Tool results, git output, file diffs, tests, builds, and explicit human
  statements carry more weight than assistant summaries.

We also compared the local =reference/html-effectiveness= examples. The useful
references were not their decoration. They showed how a single HTML file can
act as a serious review surface: dense metric rhythm, strong TL;DR band,
sticky controls, compact boards, collapsible evidence, and research-style
hierarchy.

** Decision

We turned the HTML report into an explicit audit cockpit contract.

Changed =skills/ccx-insight/HTML-REPORT.md= from a short section list into a
full product spec for a self-contained, file-openable report over
=ccx.log.v1=.

The report now has a clear information architecture:

| Section | Purpose |
|---------+---------|
| Scope header | Make the time boundary, timezone, project scope, command, schema, and truncation state impossible to miss |
| TL;DR judgment band | One synthesis paragraph with confidence and the strongest correction to naive reading |
| Data quality panel | Surface long-running containers, provider caveats, sidechains, duplicates, compactions, and truncation before narrative |
| Metrics strip | Show precise counts with precise labels, especially "source log files" |
| Workstream board | Group human-reviewable work by status: in motion, needs closure, done/achieved, watch |
| Timeline | Curated important events, not every record |
| Claim ledger | Classify consequential claims as observed, human-stated, agent-claimed, inferred, unverified, or contradicted |
| Decisions and corrections | Preserve who changed direction and why |
| Evidence drawer | Keep source paths, line numbers, snippets, and raw details available without flooding the report |
| Needs closure | Make open loops actionable without inventing owners |

We also updated =skills/ccx-insight/SKILL.md= so the top-level skill describes
HTML output as a standalone audit cockpit, not a decorative summary. Before
writing HTML, the skill must inspect provider/data-quality shape: source log
files, long-running containers, workspace split, Codex duplicate-looking
records, Claude sidechains/subagents, compaction records, and truncation.

The road not taken: add a new programmatic =ccx insight --html= or revive the
old =ccx insight= summary object. That was rejected again. The CLI should
emit evidence. The skill can interpret, but it must show its work.

The other road not taken: generate a durable repo report by default. The skill
now writes HTML to the OS temp directory by default and writes into =reports/=
only when the human asks for a durable artifact. That keeps normal use from
dirtying the release branch.

** Tradeoff

This makes the skill heavier. A future agent has more rules to follow before
it can produce an HTML report.

That cost is intentional. The feature is not trying to produce a fast pretty
page. It is trying to prevent a human from trusting a compressed status story
that the logs do not support.

The report spec still does not implement an automatic renderer. It defines
the contract for skill-generated reports. That keeps the release focused on
the evidence primitive and the agent workflow, but it means consistency
depends on agents following the skill until a renderer exists.

The report may feel less magical because it labels uncertainty. That is the
right product feel for this feature. The HTML should be useful because it is
exact, not because it pretends to know more than it knows.
